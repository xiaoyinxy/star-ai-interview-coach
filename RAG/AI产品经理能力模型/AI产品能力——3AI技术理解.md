# AI 产品经理能力模型：AI 技术理解能力

## 文档用途

本知识用于 AI 产品经理行为面试经历挖掘。

当候选人描述 AI 项目时，系统应判断候选人是否真正理解项目中的 AI 技术方案，而不是仅仅知道项目使用了“大模型、RAG、Agent、Prompt”等术语。

本知识库主要帮助模型判断：

- 候选人是否理解 AI 在产品中的作用；
- 是否理解模型输入、处理、输出的基本链路；
- 是否理解 Prompt、RAG、Agent 等技术模块分别解决什么问题；
- 是否理解方案选择背后的原因；
- 是否知道模型存在什么能力边界；
- 是否真正参与过 AI 产品方案设计，而不是只负责外围产品工作。

AI 产品经理不需要像算法工程师一样解释模型训练公式，但应该能够回答：

**为什么使用这个 AI 技术、它解决什么问题、系统是怎么工作的、哪里可能失败，以及技术能力如何影响产品设计。**

PARENT_SPLIT_9F3A

## P01 AI 技术方案整体理解

AI 产品经理首先应该能够用产品和系统视角解释自己的 AI 产品是如何工作的。

一个基本完整的 AI 系统链路通常需要说明：

用户输入什么
→ 系统如何处理输入
→ 是否进行 Prompt 构造或信息加工
→ 是否调用知识库、工具或外部系统
→ 模型完成什么任务
→ 系统如何处理模型输出
→ 最终如何呈现给用户。

候选人不一定需要知道所有底层实现细节，但应该理解自己负责的产品中核心 AI 链路。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 能清楚描述 AI 系统完整链路；
- 知道各模块分别解决什么问题；
- 能区分模型能力与产品系统能力；
- 能解释用户输入如何转化为模型输入；
- 知道模型输出后还有哪些产品或工程处理。

弱信号包括：

- “后面接了一个大模型”；
- “算法同学负责这部分，我不太清楚”；
- 只知道使用某个模型名称；
- 无法解释 RAG、Prompt、Agent 在系统中的具体作用；
- 把所有 AI 能力都归因于“模型比较强”。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人提到 AI 产品但系统链路非常模糊时，应优先追问整体架构理解。

追问目标：

判断候选人是否真正理解自己参与的 AI 产品。

推荐追问方向：

- 从用户输入到最终结果，整个 AI 链路大概是什么样？
- 大模型在这个产品里具体负责哪一步？
- 除了模型之外，系统还有哪些重要模块？
- 哪一步最容易影响最终输出质量？
- 如果把大模型拿掉，这个产品还有哪些能力可以正常运行？

PARENT_SPLIT_9F3A

## P02 模型能力与模型选择理解

不同模型在语言理解、生成、推理、多模态、上下文长度、工具调用等方面能力不同。

AI 产品经理不一定负责最终模型选型，但应理解：

为什么项目选择某种模型，以及模型能力如何影响产品方案。

模型选择不应该只是：

“哪个模型排行榜最高就用哪个。”

而需要结合任务特点判断模型是否适用。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 比较过不同模型；
- 能说明模型选择依据；
- 理解任务对模型能力的要求；
- 根据模型效果调整产品方案；
- 知道某些任务对推理、多模态或长上下文能力要求更高；
- 模型表现变化后能够判断产品受到什么影响。

弱信号包括：

- “GPT 最强所以用 GPT”；
- 完全不知道为什么选这个模型；
- 模型升级后默认所有能力都会提升；
- 不知道模型在哪些任务上表现不好。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人提到“换模型”“模型选型”“用了某个大模型”时，可以进一步深挖。

追问目标：

判断候选人是否理解模型与具体产品任务之间的关系。

推荐追问方向：

- 当时为什么选择这个模型？
- 有没有比较过其他模型？
- 这个任务最依赖模型的哪种能力？
- 有没有某类任务这个模型一直做不好？
- 模型能力最终有没有影响你的产品设计？

PARENT_SPLIT_9F3A

## P03 Prompt Engineering 理解

Prompt 不只是给模型写一句指令。

在实际 AI 产品中，Prompt 可能承担：

- 角色定义；
- 任务说明；
- 输入上下文；
- 输出格式约束；
- 行为边界；
- Few-shot 示例；
- 用户动态信息注入。

优秀的 AI 产品经理需要理解：

Prompt 是控制模型产品行为的重要组成部分，但 Prompt 并不能解决所有模型问题。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 对 Prompt 进行结构化设计；
- 区分 System Instruction 与用户输入；
- 使用 Few-shot；
- 约束输出格式；
- 针对 Bad Case 修改 Prompt；
- 记录 Prompt 版本；
- 能解释某次 Prompt 修改解决了什么具体问题。

弱信号包括：

- “优化了一下 Prompt”；
- 只是不断增加更多文字；
- 不知道哪一条 Prompt 对效果产生影响；
- 每次出现问题都通过增加 Prompt 规则解决；
- Prompt 修改没有任何验证。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人提到“Prompt 优化”“Prompt Engineering”时，不应停留在术语层面。

追问目标：

判断候选人是否真正参与过 Prompt 设计和迭代。

推荐追问方向：

- 你具体改了 Prompt 的哪一部分？
- 最初 Prompt 最大的问题是什么？
- 为什么你认为修改这条指令能够解决问题？
- 有没有使用 Few-shot？
- 有没有出现 Prompt 越写越长但效果反而下降的情况？
- 你如何避免不同 Prompt 规则之间发生冲突？

PARENT_SPLIT_9F3A

## P04 Context 与上下文管理理解

LLM 的输出不仅由模型本身决定，也受到输入上下文影响。

上下文可能包含：

- System Prompt；
- 用户当前输入；
- 历史对话；
- RAG 检索结果；
- Few-shot；
- 用户画像；
- 工具调用结果；
- 结构化状态变量。

AI 产品经理应该知道：

哪些信息需要进入模型上下文，以及上下文过多、过少或存在冲突都会影响结果。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 主动管理对话历史；
- 只向模型提供相关信息；
- 对长对话做摘要；
- 使用结构化变量保存关键状态；
- 区分长期信息与当前任务信息；
- 意识到 Context 中不同信息可能发生冲突。

弱信号包括：

- 所有历史对话全部塞给模型；
- 认为 Context 越长效果越好；
- 不知道模型为什么会“忘记”之前的信息；
- 用户历史信息与当前任务混在一起。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人描述多轮对话、长文档、智能助手或持续任务时，可以深挖 Context 管理。

追问目标：

判断候选人是否理解 LLM 产品中的上下文机制。

推荐追问方向：

- 多轮对话中你们怎么保留用户之前的信息？
- 所有历史消息都会传给模型吗？
- 哪些信息需要长期保存，哪些只在当前轮使用？
- 对话变长后有没有出现模型表现下降？
- 你们怎么处理上下文中的冲突信息？

PARENT_SPLIT_9F3A

## P05 RAG 基本原理理解

RAG 的核心目的是：

让模型在生成答案之前，从外部知识库检索与当前问题相关的信息，并将这些信息作为 Context 提供给模型。

典型链路包括：

文档
→ 文档解析
→ Chunk
→ Embedding / 索引
→ 用户 Query
→ Retrieval
→ 返回相关 Chunk
→ 放入模型 Context
→ 生成答案。

RAG 主要解决的是：

模型参数知识之外的私有知识、最新知识或特定领域知识获取问题。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 能解释为什么需要 RAG；
- 理解 Chunk、Embedding、Retrieval 的基本作用；
- 知道知识库内容会影响最终回答；
- 知道“知识库里有”不等于“一定能召回”；
- 能区分模型幻觉与检索失败。

弱信号包括：

- “RAG 就是把 PDF 喂给模型”；
- 认为模型直接读取整个知识库；
- 不知道 Chunk 是什么；
- 知识库存在答案却召回失败时仍认为是模型问题；
- 把 RAG 和 Fine-tuning 当成同一件事。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人提到知识库、企业问答、RAG 等项目时，应判断其是否真正理解基本链路。

追问目标：

确认候选人能否解释 RAG 为什么有效以及可能在哪里失败。

推荐追问方向：

- 为什么这个项目需要 RAG？
- 用户提问后，知识是怎么被找到并交给模型的？
- 如果知识库里明明有答案，但模型还是回答错了，你会先排查什么？
- Chunk 切得太大或太小可能有什么影响？
- RAG 解决了什么问题，又不能解决什么问题？

PARENT_SPLIT_9F3A

## P06 RAG 检索与知识组织理解

RAG 的效果不仅取决于模型，也高度依赖知识如何被组织和检索。

需要关注的基本概念包括：

- Chunk；
- Metadata；
- Embedding；
- Semantic Retrieval；
- Keyword Retrieval；
- Hybrid Retrieval；
- Top-K；
- Rerank。

AI 产品经理不一定负责具体算法实现，但需要知道：

检索质量会直接决定模型最终能看到什么知识。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 根据知识特点设计 Chunk；
- 使用 Metadata 组织知识；
- 知道语义搜索和关键词搜索各有优势；
- 理解候选召回和最终排序的区别；
- 分析过错误召回或漏召回；
- 能把 RAG Bad Case 定位到检索环节。

弱信号包括：

- 完全使用默认设置且不知道含义；
- 认为 Embedding 可以解决所有检索问题；
- 不知道 Top-K 为什么需要调整；
- 检索到不相关内容时只调整 Prompt；
- 不知道 Metadata 的作用。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人确实负责过 RAG 产品，且声称进行了“知识库优化”时，可以进一步深挖。

追问目标：

判断候选人对 RAG 是否已经超过“会调用组件”的程度。

推荐追问方向：

- 你们的知识是怎么分块的？为什么这样分？
- 有没有使用 Metadata？
- 你们遇到过知识存在但检索不到的情况吗？
- 什么情况下关键词检索反而比向量检索更有效？
- Rerank 在你们系统里解决的是什么问题？

PARENT_SPLIT_9F3A

## P07 RAG 与 Fine-tuning 的边界理解

RAG 与 Fine-tuning 解决的问题不同。

RAG 更适合：

- 注入外部知识；
- 私有企业知识；
- 高频更新知识；
- 需要引用来源的场景。

Fine-tuning 更偏向：

- 改变模型行为模式；
- 特定输出风格；
- 特定任务模式适配。

不能简单理解为：

“RAG 效果不好就 Fine-tune。”

也不能认为：

“Fine-tuning 可以让模型记住所有企业知识。”

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 能区分知识问题与行为问题；
- 知道什么情况适合 RAG；
- 知道什么情况可能考虑 Fine-tuning；
- 不把 Fine-tuning 当作知识库；
- 能解释为什么项目没有选择另一种方案。

弱信号包括：

- 认为 Fine-tuning 就是“训练自己的知识库”；
- 认为 RAG 和 Fine-tuning 可以随意互换；
- 没有判断问题类型就决定技术方案。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人提到 RAG、Fine-tuning 或模型定制时，可以判断技术选择逻辑。

追问目标：

判断候选人是否理解不同技术解决的问题边界。

推荐追问方向：

- 为什么选择 RAG，而不是 Fine-tuning？
- 你们的问题本质是知识不足，还是模型行为不符合预期？
- 如果知识每天变化，哪种方式更合适？
- 什么情况下你会考虑 Fine-tuning？
- RAG 做不好时，你会直接转向 Fine-tuning 吗？为什么？

PARENT_SPLIT_9F3A

## P08 Agent 基本原理理解

Agent 与普通单次 LLM 调用的区别在于：

Agent 通常需要根据目标决定下一步行为，并调用外部工具完成一个或多个步骤。

典型链路可能是：

用户目标
→ 理解任务
→ 决定下一步行动
→ 调用工具
→ 获取结果
→ 判断是否继续
→ 最终回答或执行结果。

Agent 的价值主要存在于：

需要多步骤决策、工具使用或动态任务执行的场景。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 能解释 Agent 为什么需要工具调用；
- 知道 Agent 与固定 Workflow 的区别；
- 能描述 Agent 如何决定下一步动作；
- 理解多步骤任务可能出现中间失败；
- 能判断哪些任务不需要 Agent。

弱信号包括：

- “Agent 就是更高级的 Chatbot”；
- 所有 AI 项目都想使用 Agent；
- 不知道工具调用与模型生成的区别；
- Agent 实际流程完全固定，却仍称为 Agent。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人提到 Agent 时，应避免只听概念描述。

追问目标：

确认候选人是否真正理解 Agent 的产品和技术机制。

推荐追问方向：

- 这个场景为什么需要 Agent，而不是固定 Workflow？
- Agent 可以调用哪些工具？
- 模型是如何决定下一步调用哪个工具的？
- 如果其中一次工具调用失败会怎么办？
- 哪一步是真正由 Agent 动态决策的？

PARENT_SPLIT_9F3A

## P09 Workflow 与 Agent 的选择理解

固定 Workflow 与 Agent 都可以完成复杂任务，但适用场景不同。

Workflow 更适合：

- 流程相对稳定；
- 步骤可以提前确定；
- 强调可控性；
- 希望容易 Debug。

Agent 更适合：

- 用户任务变化较大；
- 步骤无法完全提前确定；
- 需要动态选择工具；
- 需要根据中间结果决定下一步行动。

AI 产品经理需要避免为了“Agent 化”而使用 Agent。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 比较过 Workflow 和 Agent；
- 优先使用简单可控方案；
- 根据任务不确定性选择架构；
- 能解释为什么某些步骤固定、某些步骤动态。

弱信号包括：

- “Multi-Agent 更高级”；
- 简单任务也设计多个 Agent；
- 无法解释 Agent 带来的具体收益；
- 为了技术亮点增加复杂架构。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人提到 Agent、多 Agent、复杂 AI Workflow 时，应优先判断架构是否真的必要。

追问目标：

判断候选人是否具有 AI 架构复杂度意识。

推荐追问方向：

- 为什么这里不能直接用 Workflow？
- 哪些步骤是确定的，哪些步骤必须动态决策？
- Agent 架构相比普通 Workflow 带来了什么实际收益？
- 如果去掉 Agent，产品效果会损失什么？
- 你有没有为了降低复杂度主动放弃过 Multi-Agent？

PARENT_SPLIT_9F3A

## P10 Tool Calling 与外部系统理解

LLM 本身主要负责理解和生成，并不能天然完成所有现实世界操作。

如果 AI 需要：

- 查询数据库；
- 获取实时天气；
- 搜索企业系统；
- 创建日历事件；
- 操作 CRM；
- 调用搜索引擎；
- 执行业务动作；

通常需要通过 Tool Calling 或 API 与外部系统交互。

AI 产品经理需要理解：

模型决定“要做什么”，工具负责真正执行确定性操作。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 区分模型生成和工具执行；
- 明确工具输入输出；
- 对工具调用失败有处理方案；
- 知道外部数据为什么不能完全依赖模型记忆；
- 能设计人工确认机制。

弱信号包括：

- 认为模型本身可以直接获取所有实时数据；
- 让 LLM 自己生成数据库结果；
- 不区分“模型说已经操作”和“系统真的执行成功”；
- 没有工具失败处理。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人的项目包含 Agent、自动执行或外部系统集成时，可以进一步追问。

追问目标：

判断候选人是否理解 LLM 与真实业务系统的边界。

推荐追问方向：

- 这个动作最终是模型执行，还是通过 API 执行？
- 模型如何知道应该调用哪个工具？
- 工具返回结果后模型怎么继续处理？
- 如果 API 调用失败怎么办？
- 哪些工具调用需要用户二次确认？

PARENT_SPLIT_9F3A

## P11 AI 幻觉与能力边界理解

生成式 AI 的输出具有概率性。

模型可能出现：

- 编造事实；
- 错误引用；
- 错误理解用户意图；
- 输出格式不稳定；
- 对自己不知道的信息表现得过于确定；
- 在信息不足时自动补全。

AI 产品经理需要理解：

幻觉不能仅靠一句“不要 hallucinate”的 Prompt 完全解决。

通常需要结合：

- RAG；
- 工具调用；
- 输出约束；
- 来源引用；
- 用户确认；
- 规则校验；
- Fallback；
- 能力边界设计。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 主动识别幻觉风险；
- 不让模型生成无法验证的重要事实；
- 对关键事实引用来源；
- 设计用户核验；
- 将高风险任务交给确定性系统；
- 明确产品能力边界。

弱信号包括：

- “Prompt 写得好就不会幻觉”；
- 把模型输出直接当事实；
- AI 错误后只要求模型再生成一次；
- 不区分高风险和低风险内容。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人描述模型直接生成重要业务内容，但没有任何真实性机制时，应进一步深挖。

追问目标：

判断候选人是否真正理解生成式 AI 的基本限制。

推荐追问方向：

- 你们遇到过模型编造内容吗？
- 为什么会出现这类问题？
- 哪些信息绝对不能让模型自己生成？
- 你们怎么让用户知道哪些内容需要核实？
- 哪些问题应该由 RAG 解决，哪些问题不是 RAG 能解决的？

PARENT_SPLIT_9F3A

## P12 AI Bad Case 的技术定位能力

AI 产品出现 Bad Case 后，不能简单归因为：

“模型不够好。”

问题可能来自不同环节：

用户输入不清楚
→ Prompt 问题
→ Context 缺失
→ RAG 没召回
→ Rerank 排序错误
→ 模型理解错误
→ 工具调用失败
→ 输出解析失败
→ 产品交互误导。

技术理解较强的 AI 产品经理应该能够初步判断：

问题发生在哪一层。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 对 Bad Case 分类；
- 能区分 Prompt 问题与模型问题；
- 能区分 Retrieval 问题与 Generation 问题；
- 根据问题类型选择不同优化方法；
- 与算法和研发沟通时能够明确问题位置。

弱信号包括：

- 所有问题都改 Prompt；
- 所有问题都归因于模型；
- 出现错误后直接换更强模型；
- 没有 Bad Case 分类机制。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人说“我们后来不断优化 AI 效果”时，应重点深挖：

到底怎么判断问题在哪里。

追问目标：

判断候选人是否具备基础 AI 系统诊断能力。

推荐追问方向：

- 你们当时最常见的 Bad Case 是什么？
- 怎么判断它属于 Prompt、RAG 还是模型本身的问题？
- 有没有出现知识召回正确，但最终回答仍然错误的情况？
- 哪类问题最后发现换模型也解决不了？
- Bad Case 分类之后，你们分别采取了什么优化方式？

PARENT_SPLIT_9F3A

## P13 AI 技术理解的综合判断

AI 产品经理的技术理解，不是看候选人能否背出最多 AI 名词。

真正重要的是能形成以下逻辑：

用户任务
→ 判断 AI 是否适合
→ 选择适合的技术形态
→ 理解输入和 Context
→ 模型 / RAG / Agent / Tool 分工
→ 理解可能失败的位置
→ 根据 Bad Case 定位问题
→ 让技术能力服务于产品目标。

CHILD_SPLIT_9F3A

### 高质量综合信号

技术理解较强的 AI 产品经理通常能够：

- 清楚解释 AI 系统链路；
- 理解模型负责什么、不负责什么；
- 理解 Prompt 和 Context；
- 理解 RAG 的基本检索链路；
- 区分 RAG 与 Fine-tuning；
- 理解 Agent 和 Workflow 的差异；
- 理解 Tool Calling；
- 知道模型存在幻觉和能力边界；
- 能对 AI Bad Case 做基础定位；
- 能与算法和研发讨论具体问题，而不是只提出“效果再提升一点”。

CHILD_SPLIT_9F3A

### 综合追问策略

如果候选人已经充分解释某个技术环节，不应继续进行知识考试式追问。

应该寻找其项目中真正参与过、但理解仍然模糊的技术决策。

例如：

只说“用了大模型”：

优先追问系统链路和模型作用。

只说“优化 Prompt”：

优先追问具体修改和 Bad Case。

只说“用了 RAG”：

优先追问检索链路和为什么需要 RAG。

只说“做了 Agent”：

优先追问为什么不用 Workflow，以及动态决策发生在哪里。

项目效果不好：

优先追问如何判断是 Prompt、Retrieval、模型还是工具问题。

最终目标不是判断候选人是否像算法工程师一样掌握底层公式，而是判断其是否真正具备：

**理解技术能力 → 做出产品技术判断 → 与技术团队协作 → 根据系统问题持续优化**

这一 AI 产品经理所需的技术认知能力。
