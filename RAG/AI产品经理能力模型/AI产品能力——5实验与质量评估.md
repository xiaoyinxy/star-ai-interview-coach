# AI 产品经理能力模型：AI 实验质量与评估能力

## 文档用途

本知识用于 AI 产品经理行为面试经历挖掘。

当候选人描述 Prompt、RAG、Agent、大模型应用、AI 搜索、AI 客服、推荐或其他 AI 产品项目时，系统应判断候选人是否真正建立过一套可验证的 AI 效果评估方法，而不是只通过少量 Demo、主观体验或“感觉效果更好了”判断方案质量。

本知识库主要帮助模型判断：

- 候选人如何定义 AI 产品的“好”；
- 是否建立过评测数据集；
- 是否具有 Ground Truth 或参考标准；
- 是否区分离线评估和线上评估；
- 是否采用人工评测、规则评测或 AI-as-a-Judge；
- 是否比较过不同模型、Prompt、RAG 或 Agent 版本；
- 是否分析过 Bad Case；
- 是否关注平均效果之外的失败场景；
- 是否考虑 Regression；
- 是否真正通过 Evaluation 推动 AI 产品迭代。

AI Evaluation 的核心不是：

“模型跑出来一个分数。”

而是：

**把原本主观的 AI 效果，转化为可以重复测量、比较、分析和持续优化的质量体系。**

PARENT_SPLIT_9F3A

## P01 AI 产品成功标准与评估目标

AI 产品评估的第一步，是先回答：

“什么叫效果好？”

不同 AI 产品的质量目标完全不同。

例如：

AI 客服可能关注：

- 回答正确性；
- 问题解决率；
- 幻觉；
- 用户满意度。

AI 写作产品可能关注：

- 指令遵循；
- 内容质量；
- 用户采纳率；
- 修改次数。

RAG 产品可能关注：

- 是否找到正确知识；
- 最终回答是否基于知识；
- 是否完整回答问题。

因此，Evaluation 必须从真实产品任务出发，而不能简单使用一个通用“准确率”。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 在优化前明确什么叫“好”；
- 评估指标与实际产品任务一致；
- 根据不同任务设置不同质量标准；
- 同时考虑多个质量维度；
- 能解释为什么选择这些评估维度。

弱信号包括：

- “感觉回答更自然了”；
- “模型看起来聪明很多”；
- 只使用一个模糊总分；
- 不知道不同任务应该采用不同指标；
- 优化完成后才决定如何评估。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人说：

“AI 效果提升了”
“Prompt 优化后明显更好”
“模型效果不错”

但没有定义“好”的含义时，应优先追问。

追问目标：

判断候选人是否首先建立了明确的 Evaluation Objective。

推荐追问方向：

- 你们当时是怎么定义 AI 效果好坏的？
- 最核心的质量维度是什么？
- 为什么选择这些维度？
- 不同类型的问题使用同一套评价标准吗？
- 在开始优化之前，你们就定义好成功标准了吗？

PARENT_SPLIT_9F3A

## P02 Evaluation Dataset 评测集设计

稳定的 AI Evaluation 通常需要一套相对固定的测试样本。

Evaluation Dataset 的作用是：

让不同版本在相对一致的任务条件下进行比较。

评测集中的样本应尽量代表真实用户任务，而不是只包含几个容易展示效果的 Demo Case。

数据来源可能包括：

- 真实用户 Query；
- 历史日志；
- 客服问题；
- 专家构造；
- Bad Case；
- 典型业务场景；
- 边界场景；
- 高风险场景。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 建立固定 Evaluation Dataset；
- 样本来自真实用户场景；
- 覆盖不同任务类型；
- 包含正常 Case 和困难 Case；
- 随真实 Bad Case 持续补充评测集；
- 不同版本使用相同核心测试集比较。

弱信号包括：

- 每次随机测试几个问题；
- 只测试自己熟悉的 Case；
- 只选模型容易回答的问题；
- 不同版本测试不同样本；
- 无法重复验证历史结果。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人提到：

“我们测试了模型”
“人工测了几十个问题”
“做了一套测试”

时，可以进一步深挖评测集设计。

追问目标：

判断测试是否真正具有可重复性和代表性。

推荐追问方向：

- 你们的 Evaluation Dataset 是怎么构建的？
- 这些测试问题来自哪里？
- 大概有多少条？
- 如何保证它能代表真实用户场景？
- 有没有故意加入困难 Case 和 Bad Case？
- 每次版本升级都会重新跑同一套测试吗？

PARENT_SPLIT_9F3A

## P03 样本覆盖与分层评估

只看整体平均分很容易隐藏问题。

例如：

AI 客服整体正确率达到 90%。

进一步拆分可能发现：

普通 FAQ 达到 98%，但退款、支付异常等高风险问题只有 60%。

因此 Evaluation Dataset 不只是需要“足够多”，还需要有合理的数据分层。

常见分层方式包括：

- 任务类型；
- 用户类型；
- 难度；
- 输入长度；
- 业务场景；
- 风险等级；
- 是否需要外部知识；
- 是否需要推理；
- 是否需要工具调用。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 对评测集进行分类；
- 分任务类型查看效果；
- 单独关注高风险 Case；
- 不只看平均得分；
- 能发现某个局部场景严重拖后腿；
- 根据分层结果调整优化优先级。

弱信号包括：

- 只报告整体 85 分；
- 不知道哪些类型表现最好或最差；
- 大量简单 Case 掩盖困难 Case；
- 高风险任务与普通任务权重一致。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人只报告整体效果数字时，可以继续追问 Evaluation Breakdown。

追问目标：

判断候选人是否真正理解 AI 质量具有明显的场景差异。

推荐追问方向：

- 不同类型 Case 的表现一样吗？
- 哪一类问题表现最差？
- 有没有整体平均很好，但某个关键场景很差的情况？
- 你们怎么给评测集分类？
- 哪类 Case 最终成为重点优化对象？

PARENT_SPLIT_9F3A

## P04 Ground Truth 与黄金标准

要判断 AI 回答是否正确，需要尽量明确：

“正确答案是什么。”

对于确定性任务，可以建立明确 Ground Truth。

例如：

- 分类标签；
- 标准事实；
- 正确检索文档；
- 数值结果；
- 是否成功调用工具。

对于开放式生成任务，可能不存在唯一标准答案，因此可以使用：

- 评分 Rubric；
- 专家参考答案；
- 多维质量标准；
- Pairwise Comparison。

Ground Truth 的核心价值是：

让评估不完全依赖评测人的临时感觉。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 有人工标注标准；
- 有参考答案；
- 有正确文档或正确工具调用结果；
- 开放任务使用明确 Rubric；
- 标注标准经过团队对齐；
- 能处理不存在唯一答案的任务。

弱信号包括：

- “我自己觉得这个答案更好”；
- 每个评测人员标准不同；
- 没有明确正确答案或评分规则；
- 对开放式任务强行设置唯一标准文本。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人说：

“我们测试准确率”
“人工判断回答对不对”

时，应进一步确认判断依据。

追问目标：

判断其 Evaluation 是否存在相对稳定的 Ground Truth。

推荐追问方向：

- 你们怎么定义一条回答是正确还是错误？
- Ground Truth 是谁标的？
- 如果一个问题有多个合理答案怎么办？
- 标注人员之间意见不同怎么处理？
- 有没有建立统一的评分 Rubric？

PARENT_SPLIT_9F3A

## P05 人工评测 Human Evaluation

对于语言质量、帮助程度、逻辑性、自然度等开放式维度，人工评测仍然非常重要。

Human Evaluation 常用于：

- 回答正确性；
- 指令遵循；
- 有用性；
- 专业程度；
- 用户意图匹配；
- 风格；
- 安全性；
- 幻觉判断。

关键问题不只是“找人来看”，而是需要控制评价标准的一致性。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 有明确人工评分标准；
- 评测前统一标注规范；
- 重要 Case 由多人评估；
- 分析不同标注者之间的一致性；
- 使用盲测减少版本偏见；
- 对争议 Case 进行复核。

弱信号包括：

- 产品经理自己看几个 Case；
- 告诉评测人哪个版本是新版本；
- 每个人凭感觉打分；
- 没有统一评分规则；
- 人工评测结果不可复现。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人提到“人工评估”“找同学测了一下”时，可以继续判断评测质量。

追问目标：

确认 Human Evaluation 是否具有基本可信度。

推荐追问方向：

- 人工评测具体是谁做的？
- 评分标准是什么？
- 评测者知道哪个是新版本吗？
- 如果两个人给出的评价不同怎么办？
- 有没有使用盲评或者多人交叉评测？

PARENT_SPLIT_9F3A

## P06 AI-as-a-Judge 自动化评测

对于大量语言生成任务，可以使用另一个 LLM 作为 Judge，按照预定义 Rubric 对输出进行评分或比较。

AI-as-a-Judge 的优势包括：

- 成本低于大量人工评测；
- 可以快速跑大量 Case；
- 适合版本迭代；
- 能输出结构化评分和原因。

但 AI Judge 本身也可能存在：

- 偏好某种表达风格；
- Position Bias；
- 对自己模型家族存在偏好；
- 对复杂事实判断不稳定；
- 与人工标准不完全一致。

因此 AI-as-a-Judge 不能天然被视为绝对 Ground Truth。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 使用明确 Rubric；
- 结构化输出评分；
- 使用人工样本校准 Judge；
- 定期检查 AI Judge 与人工评价的一致性；
- 对关键 Case 保留人工复核；
- 对 Judge Prompt 进行版本管理。

弱信号包括：

- “让 GPT 给自己打分”；
- 默认高阶模型评分一定正确；
- 没有人工校准；
- Judge 标准频繁改变；
- Judge 和被评模型之间存在明显偏差却不处理。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人提到 AI-as-a-Judge 或自动评测模型时，应继续深挖可靠性。

追问目标：

判断候选人是否把 Judge 当成评估工具，而非绝对裁判。

推荐追问方向：

- 你们 Judge 的评分标准是什么？
- 为什么相信 Judge 的评分？
- 有没有拿人工标注去校准？
- AI Judge 和人工结果不一致时怎么办？
- 哪些 Case 不能完全依赖 AI Judge？

PARENT_SPLIT_9F3A

## P07 规则评测与可确定指标

并非所有 AI Evaluation 都需要 LLM Judge。

一些任务可以使用确定性规则进行评测。

例如：

- JSON 格式是否正确；
- 是否包含要求字段；
- Tool Calling 是否成功；
- SQL 是否能够执行；
- 是否引用正确文档；
- 是否输出敏感内容；
- 是否符合长度限制；
- 分类标签是否正确。

如果能够使用确定性评价，就不一定需要更加主观的 LLM Judge。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 能区分确定性指标和主观指标；
- 尽量使用确定性规则评测可规则化任务；
- 自动验证输出结构；
- 对 Tool Calling 结果做系统级检查；
- 人工和 Judge 只用于确实需要主观判断的维度。

弱信号包括：

- 所有东西都让 LLM 打分；
- JSON 是否正确也交给模型判断；
- 明明有客观答案却采用纯主观评分；
- 不知道哪些指标可以程序化评测。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人的项目存在结构化输出、工具调用、分类等任务时，可以判断其是否使用确定性评测。

追问目标：

确认 Evaluation 设计是否与任务性质匹配。

推荐追问方向：

- 哪些指标可以直接通过程序判断？
- 为什么这个指标需要 AI Judge，而不是规则？
- 有没有对输出格式或 Tool Calling 做自动校验？
- 哪些指标最客观、最稳定？

PARENT_SPLIT_9F3A

## P08 离线 Evaluation

Offline Evaluation 的主要目标是：

在模型、Prompt、RAG 或 Agent 版本正式上线前，通过固定评测集快速判断新版本是否整体更优。

典型流程可以是：

新版本产生
→ 在固定 Evaluation Dataset 上运行
→ 自动或人工评分
→ 与 Baseline 比较
→ 分析 Bad Case
→ 判断是否进入下一阶段。

Offline Evaluation 的优势是：

快、成本相对可控、容易重复。

但离线分数提高并不能保证真实用户体验一定提高。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 每个版本上线前都跑离线评测；
- 有固定 Baseline；
- 自动生成版本对比报告；
- 根据评测结果决定是否上线；
- 对退化场景单独检查。

弱信号包括：

- 只在开发过程中随机测试；
- 新版本感觉不错就上线；
- 没有与旧版本进行一致样本比较；
- 只关注整体分数提高。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人描述多个 Prompt、模型或 RAG 版本时，可以追问 Offline Evaluation。

追问目标：

判断模型迭代是否建立了稳定的质量门槛。

推荐追问方向：

- 新版本上线之前怎么判断它比旧版本好？
- 每次都会跑同一套评测集吗？
- 新版本需要达到什么条件才能上线？
- 有没有整体得分更高，但某些关键 Case 变差的版本？
- 如果发生这种情况，你们会怎么判断？

PARENT_SPLIT_9F3A

## P09 在线 Evaluation 与真实用户指标

Offline Evaluation 无法完全代表真实环境。

模型在真实产品中还会面对：

- 用户输入更加复杂；
- Query 分布不断变化；
- 用户可能输入测试集从未覆盖的问题；
- 产品交互会影响最终体验。

因此还需要通过线上数据验证真实效果。

常见线上信号可能包括：

- 用户采纳率；
- 任务完成率；
- 用户反馈；
- Regenerate Rate；
- 编辑率；
- 用户投诉；
- 人工转接率；
- 用户留存。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 区分离线指标和线上指标；
- 上线后继续跟踪真实用户结果；
- 比较离线分数与线上效果；
- 发现离线提升但线上效果不一致时继续排查；
- 用真实用户行为补充 Evaluation Dataset。

弱信号包括：

- 离线分数高就认为产品一定成功；
- 上线后不继续评估；
- 只看模型分，不看用户是否真正采用结果；
- 用户不满意时仍坚持离线指标很好。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人只介绍离线 Evaluation 时，可以继续询问真实用户验证。

追问目标：

判断 Evaluation 是否与最终产品价值闭环。

推荐追问方向：

- 离线分数提升后，线上用户表现也提升了吗？
- 最核心的线上质量指标是什么？
- 有没有离线评测很好，但上线之后用户并不买账的情况？
- 真实用户 Bad Case 会重新进入评测集吗？
- Offline 与 Online 指标冲突时，你更相信哪个？为什么？

PARENT_SPLIT_9F3A

## P10 版本对比与 Pairwise Evaluation

生成式 AI 的输出经常很难用绝对分数判断。

一种常见方式是：

让评测者比较两个版本：

A 和 B 哪个更好？

Pairwise Evaluation 可以减少：

“7 分和 8 分到底差多少”

这类绝对评分的不稳定性。

可以应用于：

- Prompt A vs Prompt B；
- Model A vs Model B；
- RAG 方案 A vs B；
- 新版本 vs Baseline。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 对不同版本进行同样本比较；
- 使用 Pairwise 测试；
- 隐藏版本名称；
- 记录 Win / Tie / Lose；
- 对不同任务类型分别比较版本。

弱信号包括：

- 新旧版本使用不同 Case；
- 只展示新版本好的案例；
- 评测者提前知道哪个是目标版本；
- 没有稳定 Baseline。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人说：

“V2 比 V1 好很多”
“换模型后效果提升”

时，可以进一步确认比较方法。

追问目标：

判断版本优劣是否真正经过公平比较。

推荐追问方向：

- V1 和 V2 是怎么比较的？
- 是跑相同 Case 吗？
- 有没有做盲测？
- 你们看绝对评分还是 Pairwise 胜率？
- 有没有新版本总体更好但一些场景明显退化？

PARENT_SPLIT_9F3A

## P11 Bad Case 分析与 Error Taxonomy

Evaluation 的价值不仅是得到一个平均分。

更重要的是找到：

模型究竟错在哪里。

因此 AI 产品通常需要建立 Bad Case 分类体系。

例如 RAG 问答可以拆成：

- Query 理解错误；
- 没检索到正确知识；
- 检索到错误知识；
- 知识正确但生成错误；
- 回答不完整；
- 产生幻觉；
- 引用错误。

分类之后才能选择正确的优化方法。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 系统收集 Bad Case；
- 建立 Error Taxonomy；
- 统计不同错误类型比例；
- 根据错误类型决定优化优先级；
- Bad Case 修复后加入 Regression Set；
- 能解释主要错误来自系统哪一层。

弱信号包括：

- “偶尔会答错”；
- 所有错误统一称为幻觉；
- 发现问题只改 Prompt；
- 没有系统记录失败案例；
- 同样的问题反复出现。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人说“不断优化模型效果”“分析了一些 Bad Case”时，应进一步深挖。

追问目标：

判断 Bad Case 是否真正推动系统迭代。

推荐追问方向：

- 你们最常见的 Bad Case 是什么？
- 有没有对错误进行分类？
- 哪一种错误占比最高？
- 不同错误类型分别怎么解决？
- 修复后的 Bad Case 有没有重新加入评测集？

PARENT_SPLIT_9F3A

## P12 Regression 回归评测

AI 优化经常出现：

解决问题 A，却导致问题 B 变差。

例如：

为了减少幻觉增加严格 Prompt，可能导致模型拒答率升高。

为了提升 RAG 召回，可能增加大量无关 Context。

因此修复一个 Bad Case 后，需要重新验证旧能力没有发生 Regression。

Regression Set 通常来自：

- 历史关键 Case；
- 已修复 Bad Case；
- 高风险场景；
- 核心用户任务。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 保留历史关键测试 Case；
- 修复问题后跑完整 Regression；
- 已修复 Bad Case 自动进入测试集；
- 版本升级关注能力退化；
- 不只验证当前修改的问题。

弱信号包括：

- 每次只测试正在修改的 Case；
- 修好一个问题就认为完成；
- 历史 Bad Case 后续又重复出现；
- 模型升级后没有重新测试关键场景。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

当候选人描述连续多轮 AI 迭代时，可以判断是否存在 Regression 机制。

追问目标：

判断其 Evaluation 是否真正支持长期稳定迭代。

推荐追问方向：

- 你修复这个问题后，怎么保证其他 Case 没有变差？
- 历史 Bad Case 会保留下来吗？
- 每次模型或 Prompt 升级都会重新跑哪些测试？
- 有没有出现新版本解决了一个问题，却让另一个指标下降？
- 这种情况下你们怎么做决策？

PARENT_SPLIT_9F3A

## P13 实验设计与变量控制

当比较 Prompt、模型、RAG 参数或其他方案时，需要尽量控制其他变量。

例如希望判断：

“新 Prompt 是否更好。”

那么最好保持：

- 模型一致；
- Evaluation Dataset 一致；
- Temperature 等关键参数一致；
- 评分规则一致。

否则最终结果变化可能无法判断来自哪个因素。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 一次主要调整一个核心变量；
- 对实验版本进行记录；
- 保持评测样本一致；
- 保持评价标准一致；
- 能说明实验结果主要来自什么改动；
- 对无法控制的变量保持谨慎。

弱信号包括：

- 同时换模型、Prompt、RAG；
- 最后只说整体提升；
- 不知道哪个改变产生效果；
- 每一轮使用不同测试数据；
- 实验无法复现。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

候选人说：

“我们做了很多优化后效果从 60 分升到 80 分”

时，应检查变量控制。

追问目标：

判断所谓的效果提升是否能够归因于具体优化。

推荐追问方向：

- 从 60 到 80 分中，你怎么判断是哪项改动产生的？
- 你们一次会同时改多个变量吗？
- Evaluation Dataset 前后一样吗？
- 模型和 Prompt 是否同时发生过变化？
- 哪次实验最能证明某一个策略真正有效？

PARENT_SPLIT_9F3A

## P14 Evaluation 数据闭环

成熟 Evaluation 体系不是一次性建立的。

真实用户不断产生新的问题。

因此理想闭环是：

线上用户 Query
→ 收集反馈与 Bad Case
→ 分类
→ 标注
→ 加入 Evaluation Dataset
→ 优化模型 / Prompt / RAG
→ 跑 Offline Evaluation
→ 上线
→ 再观察真实用户结果。

这样 Evaluation Dataset 会逐渐更加接近真实产品分布。

CHILD_SPLIT_9F3A

### 强信号与弱信号

强信号包括：

- 线上 Bad Case 持续进入评测集；
- 根据用户 Query 分布调整测试样本；
- Evaluation Dataset 有版本管理；
- 测试集随着产品变化而更新；
- 线上反馈真正影响下一轮研发。

弱信号包括：

- 项目初期做了一套测试集后一直不变；
- Evaluation 和用户反馈完全分离；
- 线上新问题没有进入评估体系；
- 测试集越来越无法代表真实用户。

CHILD_SPLIT_9F3A

### 触发条件与追问目标

如果候选人的 AI 产品已经运行一段时间，应进一步判断 Evaluation 是否形成长期闭环。

追问目标：

判断评测体系是否真正服务于持续产品迭代。

推荐追问方向：

- 真实用户产生的新 Bad Case 怎么进入评测体系？
- Evaluation Dataset 多久更新一次？
- 有没有因为用户行为变化重新设计评测集？
- 线上反馈如何影响下一轮 Prompt 或模型优化？
- 测试集如何避免越来越脱离真实用户？

PARENT_SPLIT_9F3A

## P15 AI Evaluation 与实验质量综合判断

高质量 AI Evaluation 并不是拥有最多指标。

真正成熟的评估体系通常形成：

明确产品任务
→ 定义质量标准
→ 建立 Evaluation Dataset
→ 建立 Ground Truth / Rubric
→ 选择合适的自动、人工或 AI Judge 方法
→ 跑固定 Baseline
→ 比较新旧版本
→ 分析 Bad Case
→ 检查 Regression
→ 上线观察真实用户
→ 将线上问题重新加入评测集。

CHILD_SPLIT_9F3A

### 高质量综合信号

Evaluation 能力较强的候选人通常能够：

- 清楚定义 AI 产品什么叫效果好；
- 构建真实且有代表性的 Evaluation Dataset；
- 对样本进行分类和分层；
- 建立 Ground Truth 或明确 Rubric；
- 合理使用 Human Evaluation；
- 理解 AI-as-a-Judge 的价值和局限；
- 尽可能使用确定性规则评估客观指标；
- 区分 Offline 和 Online Evaluation；
- 公平比较不同版本；
- 建立 Bad Case 分类；
- 建立 Regression Set；
- 控制实验变量；
- 将真实用户反馈持续加入 Evaluation。

CHILD_SPLIT_9F3A

### 综合追问策略

如果候选人已经完整说明某个 Evaluation 环节，不应继续进行知识考试式追问。

应该寻找评估链路中最薄弱的环节。

例如：

只说“测试了 100 个问题”：

优先追问这些 Case 是怎么选的。

只说“准确率 85%”：

优先追问 Ground Truth 和评分方法。

只说“GPT-4 打分”：

优先追问 AI Judge 如何校准。

只说“V2 比 V1 好”：

优先追问版本如何公平比较。

只说“解决了 Bad Case”：

优先追问是否加入 Regression Set。

只有 Offline Evaluation：

优先追问真实用户线上效果。

有很多指标但不知道最终解决什么问题：

优先追问 Evaluation 指标与产品价值之间的关系。

最终目标不是判断候选人是否记住 Evaluation 名词，而是判断其是否真正建立过：

**定义质量 → 构建数据 → 测量效果 → 定位问题 → 验证优化 → 防止退化 → 线上闭环**

这一完整的 AI 质量评估体系。
